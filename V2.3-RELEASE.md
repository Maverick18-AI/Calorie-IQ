# CalorieIQ 2.3 — local release candidate

Version: **2.3.0-dev.1**, development generation **3**.
Base checkpoint: `dab77c53af52b08668e2f279161119b3e4f0006c` (published 2.2).

This update is prepared on local `development/v2`. No push, merge into `main`,
Pages publication, credential access, package installation or system-setting
change is part of this assignment. Publishing requires the owner's next approval.
The existing public site remains on its previously published version.

## Interface changes

- Five navigation destinations: **Food Log, Recipes, Nutrition, Weight, Goals**.
  Add Food is reached from Food Log, with Food Log highlighted as its parent.
- The daily calorie/macro summary remains above a single meal dropdown. Only the
  selected Breakfast/Lunch/Dinner/Snacks group is rendered. Daily totals continue
  to include all meals, regardless of the filter.
- Empty meals have no repeated empty-state paragraph. Selected-meal calories and
  one prominent Add Food action remain. Edit, duplicate, move, delete and Undo
  operate on the underlying snapshots. A moved entry appears in its destination
  meal; successful logging selects the logged meal so its entry is visible.
- Add Food starts with **Search or manual entry** and **Scan barcode**. Search
  includes recent/favorite/frequent/saved/custom/recipe shortcuts and a Manage
  saved foods disclosure for editing, favorites and removal.
- Barcode scanning remains one primary action. Typed barcode entry is also
  accessible under secondary options, without first requesting camera permission.
  Photo decoding, supported torch/zoom, package review and local corrections remain.
- Selecting a food focuses its review and closes the search/scanner panels.
  Returning to an unfinished food retains its draft. A back action returns to
  Food Log; navigation still cancels outstanding requests and stops the camera.
- Secondary Add Food options contain quick-add calories, reusable saved meals,
  recipe access, copying any/previous day, and saving the current Food Log as a
  reusable meal. These tools are no longer on the main Food Log screen.
- Recipes focuses on saved recipes and the builder, with an Add an ingredient
  action. Saved foods are managed within Add Food rather than being deleted.
- Nutrition shows one date with previous/next arrows and a centered native date
  control. Opening Nutrition follows the selected Food Log date; its arrows/date
  picker then browse independently without changing a food draft's logging date.
- The daily/seven-day selector and Energy from Macros presentation are removed.
  Nutrient arithmetic and the separately tested macro-energy calculation remain.
- Compact nutrient rows show genuine recorded zero as zero, unavailable values
  as `—`, and partial known totals with `*` and one shared explanation. A missing
  nutrient is not treated as zero. Date-specific targets and progress remain.
- Orange/blue/navy branding, light/dark themes, safe areas, responsive layouts,
  touch targets, keyboard skip navigation and offline shell are retained.
- A compact development banner keeps the build visible; its full reset explanation
  lives once in Goals/settings and is hidden when development mode is disabled.

## Single-user behavior and data safety

The Tracking For selector and profile creation/rename/delete UI and handlers are
removed. The app keeps the **existing active ID**, rather than selecting the first
profile or creating a replacement empty user. Archived profiles from older
versions stay in storage and in exported backups; they have no switching UI.
Restoring a backup uses its validated active user and retains its other records.
Draft recovery does not silently switch to another old profile.

The version-2 database format, localStorage keys, nutrition values, saved-food and
recipe snapshots, legacy import support, backup validation/recovery, writer lock
and conflict checks remain. The only `core.js` change is Food Log terminology in
an error message. No calorie/macro/serving calculation was changed. No significant
files or actual user records were deleted during development/testing.

As explicitly requested, the existing development reset architecture remains:
both build ID and generation are advanced. **When this development candidate is
eventually installed, it resets CalorieIQ-owned test storage once.** Ordinary
reopens of this same build preserve new entries. Unrelated browser keys and
downloaded backups are unaffected. Production-mode upgrades retain records.
The interface reorganization itself introduces no data reset or schema migration.

## Limitations and pending checks

- No physical iPhone 16 Safari/Home Screen/camera/VoiceOver verification was
  performed here. Desktop viewport and simulated camera tests do not establish
  real-device recognition or permission behavior.
- External food lookup was mocked for deterministic regression tests. Live Open
  Food Facts availability was not rechecked in this 2.3 assignment. Its previously
  observed search outages and inaccurate product records remain possible.
- Local storage remains device/browser specific. Accounts and cloud sync were
  deliberately not introduced. Older archived profiles are retained in backups,
  rather than exposed as a multi-user interface.
- Development generation 3 intentionally clears test data once on installation;
  export anything experimental that you want to keep before authorizing deployment.
- All requested local interface changes are implemented. Publishing is pending
  explicit approval, not a technical blocker or an incomplete implementation.

## iPhone 16 acceptance checklist after an approved publication

1. Confirm the 2.3 banner and five navigation labels in Safari and the installed
   Home Screen app. Check portrait, landscape, larger text and both themes.
2. Select each meal. Add, edit, move, duplicate, delete and Undo; confirm the daily
   summary still includes foods from every meal. Empty meals should stay uncluttered.
3. Try Search or manual entry, recent/favorites, managing saved foods, quick add,
   saved meals, recipe ingredients and reuse-day tools. Verify draft retention when
   returning to Food Log and reopening Add Food.
4. Launch Scan barcode, stop/restart, allow/deny permission, background/return,
   photo decoding and typed UPC entry. Check serving corrections and saved overrides
   against the physical package; confirm the camera indicator turns off on exit.
5. Use Nutrition's arrows and date picker. Compare totals and date-specific goals
   with Food Log; confirm genuine zeros versus missing-value dashes. An unfinished
   food's logging date and contents should remain unchanged.
6. Reopen the same build, test offline logging after caching, and export/restore a
   test backup through Files. Confirm only one development reset and no profile UI.

## Approval needed for publication

The next approved release would safely integrate the local checkpoint with `main`
and push to the existing repository, triggering its existing Pages deployment.
It would update public application files and activate the development test-data
reset, without deleting PC files or changing hosting settings. Risks include stale
Safari caches, device-specific regressions, external food-service outages and loss
of experimental app records through the intentional development reset. Unexpected
remote changes must stop integration rather than be overwritten or force-pushed.
