# CalorieIQ 2.6 search and nutrition API review release

Candidate **2.6.0-dev.2**, generation **8**, based on the clean published
`25d1e83b75dd62432a8a16eccfd5af0b4f65d749` checkpoint. Remote history was fetched
and checked before release; development uses `development/v2` and a safe
fast-forward of `main`. The existing GitHub Pages source is `main`, repository
root, with HTTPS enforced. No second repository or site is involved.

## What ships

- Better saved/USDA/OFF relevance with brand matching, apostrophes, accents,
  plural normalization and conservative one-edit spelling fallback. Approximate
  matches are labeled. Raw/cooked, skin/skinless, salted/unsalted and other
  preparation terms are not fuzzy-matched as equivalent. Saved barcode
  corrections remain first; unrelated foods/conflicting nutrition are never
  averaged. Duplicate suppression uses identity, name, portion and nutrition.
  Corrections are selected newest-first before relevance ranking, so an older
  shorter name cannot displace newly corrected barcode nutrition.
- Search submissions debounce 200 ms. Editing the query, leaving Add Food or
  starting another operation invalidates old requests. At most two provider
  tasks run concurrently, with 12-second deadlines, bounded query/results and
  source-specific failure states. Failed sources are distinguished from no
  matches; working local results remain accessible.
- A separate [fictional, read-only search demo](dev/provider-demo.html) exercises
  synthetic grocery/restaurant results alongside real USDA, fractional portions,
  unknown nutrition, compatible units and simulated provider errors. It neither
  reads nor writes the diary and has no save/log/export actions. No actual
  FatSecret data is present.
- Restricted provider markers are rejected by food/backup validation, recipe
  creation and food review. Nested ingredients are also checked. This is a
  persistence boundary, not a way to license unknown content or prevent someone
  deliberately stripping metadata.
- The offline shell includes the small policy module. Its navigation fallback
  now applies only to the app root/index; separate pages are no longer replaced
  with app HTML. Demo assets are not precached. The `cache:'reload'` correction
  for coherent service-worker installs remains intact; USDA stays lazy loaded.

## Data preservation

This assignment explicitly requires existing diaries to remain intact, so the
candidate sets **`resetData:false`**, retaining development branding/update
behavior without the prior destructive development reset. Existing diary,
legacy/recovery keys and session drafts are preserved across this upgrade.
Future releases should keep this flag false unless a reset is explicitly
approved. Production-mode preservation and older reset-mode behavior remain
covered by regression tests.

There is no diary schema, backup-format or nutrition-engine change. Existing
version-1 migration and unrestricted version-2 backups remain supported.
Historical recipes/logs are not recalculated. No existing data was cleared in
the owner's browser; tests use disposable contexts. Local profiles still are
not secure authenticated family accounts; no cloud diaries or synchronization
were added. Browser storage eviction/device loss still require backups.

## Performance observations

Final desktop Edge measurement at **393×852**, **4× CPU throttle**, local HTTP:
USDA cold search **296.1 ms**; seven warm queries **7.8–20.3 ms**, including
banana, cooked chicken breast, raw potato, cooked white rice, plain Greek
yogurt, ground beef and raw egg. Index plus one selected detail required three
requests (manifest, index, shard). Retained JS heap increase was about **6.65 MB**.
These exclude the 200 ms submit debounce and are not physical iPhone/network
timings. Fuzzy matching is bounded and used only without exact/prefix matches;
its accuracy remains heuristic. Real brand examples rely on existing OFF, not
the fictional demo or an expanded licensed dataset.
